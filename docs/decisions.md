# Decision log

Consequential implementation choices, newest phase first. Routine reversible choices stay in code; cross-phase consequences live here and in handoff.md.

## Phase 5 — Editing and organizing requests

- **`UpdateRequest` takes the caller's source revision.** The first cut loaded the collection internally and saved against that fresh revision, which would have let a long editor session silently overwrite a competing save (exactly what the storage contract forbids). Now `UpdateRequest(path, req, expected)` forwards `expected` to `SaveCollection`, whose under-lock reread/compare is the single authoritative check — the CLI keeps no pre-check of its own, so there is no check-then-save window. An editor conflict therefore produces `*ConflictError` (exit 7) with the rejected candidate preserved in `.req/recovery/`.
- **`request edit` edits only the `request` payload** (the exact JSON `request show` prints, strict-decoded with unknown-field and trailing-data rejection). `name` and `id` are identity, managed by `rename`/`move`; IDs survive rename/move per the storage contract. Unchanged bytes → no write at all. Invalid JSON → the edit is preserved via the now-public `store.SaveRecovery` (extracted from `conflict()`, same naming and 0600), exit 2. Editor failure → the temp `req-edit-*.json` is kept and named (nothing else preserved the edit yet).
- **Editor launch is shell-free by spec:** `$EDITOR` beats `$VISUAL` (blank values count as unset; both unset → setup instructions, exit 2); the value is whitespace-split into argv and executed via `exec.Command`. Consequence: editor arguments containing spaces are not expressible (a quoted `sed` expression breaks) — such editors must be wrapped in a script. Verified by a real smoke launch (`EDITOR="sed -i s/GET/PUT/"`).
- **Move semantics:** `move SRC DEST` — DEST names the destination *parent* (existing folder or single-segment collection root); the item keeps its name and ID and is appended as the LAST child. Same-parent move = no-op (no write, and checked before the cycle test so it is not misread as a cycle). Cycle rule: destination item-segments having the source item-segments as a prefix (equal or longer) → `ErrBadMove` → exit 2. Cross-collection detection is lexical on the first segment (fires even when the other collection does not exist); the cycle check likewise fires before destination existence is resolved.
- **Deletion semantics:** nonempty folder/collection requires `--yes` or an interactive y/N on a terminal stdin; EOF/decline prints "deletion aborted" and exits 0 with nothing deleted; non-terminal stdin without `--yes` exits 2 with a pointer to `--yes`. Empty folders/collections and single requests delete without confirmation (`--yes` is accepted on `request delete` for symmetry). `DeleteCollection` checks the caller's revision under the workspace lock before `os.Remove`; a conflict carries no recovery file (a delete has no candidate content). Confirmation hooks (`stdinIsTerminal`, `confirmDelete`) are package vars so tests never need a pty.
- **Exit-code mapping extended:** `ErrBadMove` joins the sentinels mapped to 2 in `usageOrStorage` — a bad move is a usage problem, not storage damage.

## Phase 4 — Collections, folders and saved requests

- **Slash paths address collections by Name, not ID.** The CLI contract (`req tree "My API"`, `req run "My API/Auth/Login"`) is name-based; duplicate collection names are therefore rejected at create (`ErrDuplicateName`), making names unique keys. Name resolution (`collectionByName`) strict-loads every collection file, in sorted-filename order — deterministic and honest about malformed files (they fail the command with exit 7 rather than being skipped).
- **`--parents` creates missing ancestor folders only, never the collection.** A missing collection is always "not found" (exit 2); collection creation stays the dedicated `collection create` command. Request create accepts `--parents` too (the spec's rule "creating missing ancestors requires `--parents`" is generic, not folder-specific).
- **One execution path for send and run.** `internal/execution.Prepare(saved, overrides, policy)` + `Execute` is the single send/render core; `runSend` and `runRun` both go through it. Overrides are structural only (`method/url/body` replace; `header`/`query` entries **append after** saved ones — matching §3's "repeated query/header flags append entries"); HTTP policy (timeout/TLS/redirects/fail) is a separate `Policy` struct so callers can't accidentally leave redirects off (the CLI default is follow). `run` never writes the collection file back.
- **Remaining `{{…}}` placeholders fail execution with exit 2 — including direct `req send`.** Substitution arrives in Phase 6+; until then any placeholder in method/URL/headers/body is "unresolved" and a literal placeholder is never put on the wire. This deliberately tightens Phase 2 behavior (a `{{…}}` in a send URL used to be sent literally); `Prepare`'s placeholder check is what enforces it for both entry points, and the error names the placeholder and the field.
- **`--json` validation timing follows §3:** validated immediately at `request create` / `run` parse time only when the text contains no `{{` (placeholders may make it valid JSON only after substitution; then it is stored/passed verbatim). Placeholder-free invalid JSON stays a usage error (exit 2) at the earliest opportunity.
- **Exit-code split for store-backed commands:** `ErrNotFound`/`ErrInvalidPath`/`ErrDuplicateName` → 2 (usage/lookup), everything else from the store (IO, lock, `*ConflictError`, malformed file) → 7. Model-level validation errors carry no sentinel, so handlers pre-validate the user-facing ones (collection name, method token, non-empty URL, entry shapes) to keep them at exit 2. Concurrent creates both load the same revision → the loser gets `*ConflictError` (exit 7) with a recovery file, per the storage contract.
- **Output channels:** CRUD status messages go to stderr; `collection list` (`NAME\tID`), `request list` (`NAME\tMETHOD\tURL`), `request show` (indented JSON of the stored request) and `tree` go to stdout so they pipe cleanly. Sibling order is always stored (insertion) order — "stable" means stable across invocations, not sorted; only `collection list` sorts (by name, because directory order is not stable).
- **Tree format:** root line (collection or resolved folder name), children flush-left beneath it, one 2-space indent per deeper level; folders render `Name/`, requests `Name  METHOD URL`. Requests-as-leaf details keep the tree useful without a second command.

## Phase 3 — Workspace and atomic persistence

- **Native schema shape:** items are tagged `{"type":"folder"|"request","id","name"}` with an exclusive `folder`/`request` payload object (flat enough to eyeball, unambiguous to validate). Entries are ordered `{key,value,enabled}` lists; `Auth`/`Body`/`Scripts` are tagged structs; nil `Auth`/`Scripts` mean "not set" (= inherit for items). Strict decode (`DisallowUnknownFields` + trailing-data rejection) is the enforcement point for "unknown fields must be rejected rather than silently discarded" — all loads go through `LoadCollection`, never a bare `json.Unmarshal`.
- **Names reject `\` as well as `/`.** The spec names `/` only, but Windows treats backslash as a path separator; accepting it would let an item name escape its directory there. Duplicate sibling names are rejected across types; IDs must match `[A-Za-z0-9_-]{1,64}` (also the filename-safety rule).
- **Revision = SHA-256 of the exact file bytes** (opaque to callers). Saving requires the loaded revision back; a missing expected revision on an existing file is also a conflict, so nothing can blindly overwrite. Conflict path: the rejected candidate is preserved under `.req/recovery/<id>-<hash>.json` (0600) and the error names it — this is the "recovery path" the storage contract requires.
- **Lock choice:** `github.com/gofrs/flock v0.13.1` (MIT) over `.req/.lock`, acquired with `TryLockContext` (honors ctx cancellation; 50 ms retry). The lock covers reread → compare → atomic replace. Verified by tests: 8 concurrent same-revision writers yield exactly 1 winner; a save cannot complete while another holder has the lock.
- **Atomic replace:** temp file in the destination directory (`.name.tmp-*`), write → `Sync` → `Close` → `Chmod` → `Rename`; failed attempts remove the temp and never touch the destination. Applied to collections, config.json and .gitignore alike.
- **`req init` accepts `--workspace` before or after the subcommand** (a smoke test caught the trailing form failing). For commands with value-taking flags (`send`), global flags are still only recognized before the subcommand so they can never be swallowed as a flag value.
- **Deferred representation question (Phase 7):** raw/JSON bodies with neither `text` nor `file` currently validate (empty string + omitempty makes "explicitly empty" ambiguous on disk). If empty-vs-absent must round-trip, switch `Body.Text` to `*string` then; noted here so it is a conscious choice.

## Phase 2 — HTTP methods, bodies and failures

- **Credentials follow redirects only within the exact origin (scheme + host + port), stricter than net/http.** Verified against the Go 1.25 source: `Client.do` compares domain names (`isDomainOrSubdomain` over IDNA hosts), so the stdlib forwards `Authorization`/`Cookie` across ports and on an https→http downgrade to the same host. Our `Client(Options).CheckRedirect` deletes the sensitive header set (`Authorization`, `Proxy-Authorization`, `Cookie`, `Cookie2`, `Www-Authenticate`, `Proxy-Authenticate`) whenever the redirect leaves the original origin, and keeps them on same-origin redirects. Subdomain forwards are also stripped (no `--location-trusted` equivalent until a phase asks for one); explicit `:80`-style ports are compared literally, so a default-port URL may be over-stripped — the fail-safe direction. This behavior applies to main and (later) auxiliary script requests because both use `httpclient.Client`.
- **Client policy moved into `Options`/`Client(opts)`** (`internal/httpclient/build.go`); `DefaultClient()` = `Client(Options{})`; `Send` untouched. Phase 3+ selects per-execution policy (timeout, insecure, redirects) through `Options`.
- **Send flag parsing is strict and additive.** Repeated `-H/--query` append entries; `--query` appends onto the existing URL query without re-encoding it (duplicates and empty values survive byte-for-byte). `--body`/`--json` are the only body modes until Phase 7; JSON is validated (exit 2) before sending; generated Content-Type (`application/json` / `text/plain`) loses to any explicit `Content-Type` header. Positional `METHOD URL` and `--method`/`--url` are mutually exclusive; unknown flags and extra positional arguments exit 2.
- **Go 1.25 renamed the redirect sentinel:** `http.ErrUseLastResponse` (the old `ErrUseOfLastResponse` no longer exists) — used for `--no-follow`.

## Phase 1 — Embedded JavaScript feasibility

- **Runtime chosen: `github.com/dop251/goja`, pinned at `v0.0.0-20260903201622-f87b40ad7341`.** Resolved via `go get @latest` on 2026-09-05 with Go 1.25.5; commit dated 2026-09-03, so the project is actively maintained. License: MIT (verified in the module cache). All five feasibility tests pass under `-race`.
- **Goja fact that shapes the event loop:** this version has no `ExecuteDeferredJobs`; promise reaction jobs run automatically whenever the JS stack empties — after `RunProgram` and after each owner-thread `Callable` invocation. The drain loop therefore only needs the pending-host-task counter; reactions that schedule more host work raise the counter again before the check.
- **Interrupt handling:** `rt.Interrupt` is the only cross-goroutine runtime call (watchdog only). It latches if the runtime is idle, so each run starts with `ClearInterrupt()` — safe because the previous run's watchdog has provably exited before `Run` returns. `Run` reports either `*goja.InterruptedError` or the context error for the same cancellation; tests accept both, and the production exit-code mapping (130/3) is applied later.
- **Late completions:** every completion job carries the run-generation token of the run that scheduled it; if the run has ended (or its context is gone) the job is discarded without touching JS values. `Close` drops queued jobs via a `quit` channel so senders never block or panic.
- **Spike bindings (`vars`, `log`, `httpGet`, `httpGetAsync`) are throwaway.** They prove ownership/interruption/async only; the supported pm surface is built in Phases 8–12 and is not wired into the CLI yet. Spike body cap is a fixed 1 MiB placeholder; the configurable 10 MiB policy comes with production bindings.

## Phase 0 — Core / Walking Skeleton

- **Module path is `req`, module rooted at the repository root.** No hosting/domain prefix; the binary is the deliverable and nothing is published. Imports read `req/internal/...`. No third-party dependencies yet.
- **Argument parsing is strict positional parsing inside `internal/cli`, not the `flag` package yet.** `req send METHOD URL` must be exactly two arguments; anything else (unknown command, missing/extra args, schemeless or non-http(s) URL) exits 2 with usage. Nothing is silently dropped; flags join in Phase 2 ("keep argument parsing replaceable").
- **A status/duration line goes to stderr on every successful send** (`GET url -> 200 OK in 1.2ms`), per IMPLEMENTATION.md §6 ("stderr contains status, elapsed time"). Stdout stays body-only.
- **Context cancellation maps to exit 130** (`signal.NotifyContext` in main; `runSend` checks `ctx.Err()` after a Send error). Transport errors otherwise map to 3; body-read failure after received headers also maps to 3.
- **`httpclient.Send` rejects non-http(s) schemes defensively** even though the CLI already validates (exit 2 first). The CLI check owns the user-facing message.
- **`Version = "0.0.1"` is a constant in `internal/cli`**; `--help`/`help` prints usage to stdout with exit 0. Build-info stamping deferred; trivial to add at delivery.
- **No VCS initialized.** The directory was not a git repository and none was requested; handoff.md tracks working-tree state instead. Initialize git whenever the user wants per-phase commits.
